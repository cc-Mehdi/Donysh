# خط مبنای فنی اکوسیستم دونیش

تاریخ بررسی: ۱۴۰۵/۰۷/۲۶ (۲۰۲۶-۱۰-۱۸)

این سند نتیجهٔ بررسی سورس واقعی مخزن است و مبنای تغییرات مرحله‌ای بعدی خواهد بود.

## ساختار موجود

- Solution اصلی `HesabYar.sln` پیش از این مرحله فقط پروژهٔ `HesabYar.Web` را داشت. پروژه‌های آزمون و موبایل خارج از Solution بودند.
- اپلیکیشن مالی یک برنامهٔ ASP.NET Core Razor Pages روی `.NET 10` است. `global.json` نسخهٔ پایهٔ SDK را `10.0.100` با `latestFeature` تعیین می‌کند.
- رابط وب با Tailwind CSS 4 ساخته می‌شود. فایل‌های استاتیک در `HesabYar.Web/wwwroot` هستند.
- پایگاه‌داده PostgreSQL 17 است و در Compose با image رسمی `postgres:17-alpine` اجرا می‌شود.
- استقرار فعلی با Docker Compose، Caddy و `scripts/server-deploy.sh` انجام می‌شود. Caddy گواهی HTTPS را مدیریت می‌کند.

## احراز هویت و کاربران فعلی Finance

- Finance از ASP.NET Core Identity و Cookie اختصاصی خودش استفاده می‌کند.
- `ApplicationUser` از `IdentityUser` ارث می‌برد و `DisplayName` و `CreatedAtUtc` دارد.
- شناسهٔ کاربر از نوع `string` است و کلید خارجی رکوردهای مالی، عضویت فضا، اقساط، پیامک‌ها و دعوت‌ها به آن وابسته‌اند.
- رمزها با قالب پیش‌فرض `PasswordHasher` در ASP.NET Core Identity ذخیره می‌شوند؛ آزمایش سازگاری نشان می‌دهد همان Hash در سرویس Auth جدید قابل اعتبارسنجی است.
- جدول‌های Identity و داده‌های مالی در یک `ApplicationDbContext` و یک پایگاه‌داده قرار دارند.
- Finance فعلاً ثبت‌نام را انجام می‌دهد و ایمیل را هنگام ساخت حساب تأییدشده در نظر می‌گیرد؛ سرویس ارسال ایمیل عملیاتی در مخزن وجود ندارد.

## ساختار داده و Migration فعلی

- Finance از EF Migration استفاده نمی‌کند. `DatabaseInitializer` ابتدا `EnsureCreatedAsync` و سپس مجموعه‌ای از دستورهای SQL سازگار و تکرارپذیر را اجرا می‌کند.
- این الگو برای دیتابیس تازه کار می‌کند، ولی تاریخچهٔ رسمی Schema ندارد و تبدیل مستقیم آن به Migration ریسک بالایی دارد.
- Auth جدید از ابتدا DbContext و Migration مستقل دارد و هیچ دستور Schema روی دیتابیس Finance اجرا نمی‌کند.

## زیرساخت و پیکربندی

- Secretهای عملیاتی از `.env` خوانده می‌شوند و `.env` در Git نادیده گرفته شده است.
- کلیدهای Data Protection اپلیکیشن مالی در volume ماندگار ذخیره می‌شوند.
- Compose فعلی فقط `db`، `web` و `caddy` را دارد. فایل آن در این مرحله تغییر نکرده است.
- CI روی Ubuntu، .NET 10، Node.js 22 و PostgreSQL 17 اجرا می‌شود؛ CSS، Build، آزمون‌های API/SMS و Docker image را بررسی می‌کند.
- سرویس Background Job، Analytics و سرویس ایمیل پیکربندی‌شده‌ای در Finance پیدا نشد.
- در `CI-CD.md` یک health URL قدیمی با دامنهٔ `novyx.ir` وجود دارد که باید در یک تغییر مستندات جدا اصلاح شود؛ اسکریپت واقعی استقرار از `DOMAIN` استفاده می‌کند.

## فونت و دارایی برند

- فایل‌های `YekanBakh-Regular.woff2` و `YekanBakh-Bold.woff2` در پروژهٔ Finance وجود دارند و Auth آن‌ها را به‌صورت لینک‌شده استفاده می‌کند تا کپی اضافه تولید نشود.
- فایل IRANYekanX دارای مجوز قابل اثبات داخل مخزن پیدا نشد. بنابراین نسخه‌ای از اینترنت یا فایل تجاری بدون مجوز به مخزن افزوده نشده است. CSS نام IRANYekanX را در اولویت می‌گذارد و سپس از YekanBakh موجود استفاده می‌کند.

## ریسک‌های اصلی

1. جداسازی جدول کاربران از دیتابیس مالی می‌تواند تمام کلیدهای خارجی مبتنی بر User ID را بشکند؛ حفظ ID یا نگاشت پایدار الزامی است.
2. ثبت‌نام هم‌زمان در Finance و Auth می‌تواند حساب تکراری بسازد؛ ثبت‌نام و بازیابی Auth تا پایان Import کاربران با دو قفل تنظیماتی بسته است.
3. نبود Migration رسمی در Finance، Rollback تغییر Schema آن را دشوار می‌کند؛ مرحلهٔ اول به Schema مالی دست نمی‌زند.
4. جابه‌جایی دامنه روی Cookie، Callback، لینک‌های موبایل و آدرس‌های hardcoded اثر دارد؛ این کار متعلق به مراحل ۲ و ۳ است.
5. گواهی‌های امضا/رمزگذاری OIDC و کلیدهای Data Protection باید ماندگار و خارج از Git باشند؛ حذف آن‌ها نشست‌ها و Tokenهای معتبر را از کار می‌اندازد.

## خط مبنای Rollback مرحلهٔ ۱

- Compose و Caddy فعلی بدون تغییر باقی می‌مانند.
- استقرار Auth فقط با `docker-compose.platform.yml` انجام می‌شود.
- برای برگشت، سرویس‌های `auth` و `auth-db` از مسیر درخواست خارج می‌شوند و Caddy دوباره با `docker-compose.domain.yml` اجرا می‌شود؛ volume دیتابیس Auth حذف نمی‌شود.
- چون Finance هنوز OIDC client نیست، خاموش‌کردن Auth هیچ اثری بر ورود یا داده‌های Finance ندارد.
